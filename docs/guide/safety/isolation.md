# Isolation

By default setup, the agent and the checks run as you:

```yaml
isolation: user # default: none; or container
```

- **`none`:** as you. [Safety](./index.md)'s measures keep credentials out of the agent's way, not its reach ([Not a sandbox](#not-a-sandbox)).
- **`user`:** as `awaywork`, a user with nothing of yours, which you make once on Linux; `awaywork-<profile>` on your machine for a [profile](../config/index.md) other than `default` (`awaywork` on a hosted runner and in the image, below).
- **`container`:** a fresh container of the repo's image per command: [In a container](#in-a-container).

`doctor` says how to make the user, here for a user `runner` (uid and gid 1001):

<!-- Generated by `pnpm docs:gen` from scripts/screens.ts. Do not edit. -->

```text config-doctor-isolation-user
✖  isolation: user, but can't run as the awaywork user (sudo: unknown user awaywork); make the worker user once:
    sudo useradd --no-create-home --user-group --shell /usr/sbin/nologin awaywork
    echo awaywork | sudo tee -a /etc/cron.deny /etc/at.deny
    sudo visudo -f /etc/sudoers.d/awaywork   # with these two lines:
    runner ALL=(awaywork) NOPASSWD:SETENV: ALL
    runner ALL=(root) NOPASSWD: /usr/bin/chown -R -h -P awaywork\: /tmp/awaywork-[A-Za-z0-9][A-Za-z0-9][A-Za-z0-9][A-Za-z0-9][A-Za-z0-9][A-Za-z0-9], /usr/bin/chown -R -h -P 1001\:1001 /tmp/awaywork-[A-Za-z0-9][A-Za-z0-9][A-Za-z0-9][A-Za-z0-9][A-Za-z0-9][A-Za-z0-9]
```

No home, no login shell: each clone gets a fresh `HOME`. The first sudoers line runs anything as the worker; the second only the two `chown`s that hand it a clone and its `HOME` and take them back ([why that's safe](#a-worker-user-on-your-linux-machine)). Then `doctor` says `✔  isolation: user: setup, the agent and the checks run as awaywork`. What changes:

- **Logins.** Your keychain login isn't there: give Claude a `CLAUDE_CODE_OAUTH_TOKEN` (`claude setup-token`) in the env file; `doctor` warns until you do. Cursor needs `CURSOR_API_KEY` anyway. Codex borrows your `auth.json` for the run and its refreshed tokens are saved back, under Codex's lock; read [what that doesn't close](#a-worker-user-on-your-linux-machine) first.
- **Only the env it needs:** `PATH`, `LANG`, `LC_*`, `TERM`, `TZ` and `CI`, the `DISABLE_AUTOUPDATER` and `GIT_AUTHOR_*`/`GIT_COMMITTER_*` names that awaywork's image and action set, awaywork's placeholders, git config and prompt path, the proxy's names, and that phase's secrets by name. Nothing else of yours, whatever your env or env file holds: a toolchain that reads, say, `JAVA_HOME` or `NPM_TOKEN` doesn't get it, and the step's `worker.log` names what each phase left out, never the values (`env: not passed to the worker user: JAVA_HOME, NPM_TOKEN`). A toolchain's own names, `JAVA_HOME` say, go in `/etc/environment`, which sudo reads for the worker on Ubuntu and in awaywork's image; on Debian add `session required pam_env.so readenv=1 user_readenv=0` to `/etc/pam.d/sudo` first.
- **Tools** must be system-wide: the worker can't run what nvm, `~/.local/bin` or `~/.cargo` put in your home, and `doctor` warns about each such `PATH` entry. For Cursor: `sudo env HOME=/opt/cursor bash -c 'curl https://cursor.com/install -fsS | bash'`, then link `agent` into `/usr/local/bin`.
- **Your home** must be closed (`chmod o-rwx ~`); `doctor` warns until it is.
- **Linux only:** `isolation: user runs on Linux only, not darwin`.
- **Always on** a GitHub-hosted runner and in awaywork's image, whatever the config says; the action or the [Dockerfile](../scheduling/container.md) makes the user.
- **One developer per worker user:** the `chown` line reaches anyone's awaywork clones.
- **A network wall:** the kernel leaves the worker only loopback, and awaywork's proxy lets each phase reach its own hosts: [the network under `user`](#the-network-under-user). `doctor` prints the lines root runs once (`iptables` rules, and a denial of the resolver's sockets), and `run` refuses until they're in.

## In a container

```yaml
isolation: container
repos:
  acme/api:
    image: ghcr.io/acme/api-dev:latest # what setup, the agent and the checks run in
    setup: pnpm i --frozen-lockfile
```

The one for your Mac, and for more than a user hides on Linux. Every setup, agent run and check starts a fresh container of the repo's `image` (Docker Desktop, Colima or Linux's engine). It mounts the clone, at its own path, and the skills plugin read-only, nothing else: no home, no docker socket. It runs as your uid and gid, every capability dropped, `no-new-privileges`. `doctor` checks Docker, each image (pulling it if missing, failing if it can't) and the agents' CLIs in it:

<!-- Generated by `pnpm docs:gen` from scripts/screens.ts. Do not edit. -->

```text config-doctor-container
✔  isolation: container: setup, the agent and the checks run in a fresh container of the repo's image (Docker 27.4.0)
✔  network wall: containers join an internal network whose only way out is a forwarder to awaywork's proxy: setup, the checks and the agent go to the hosts of their phase
✔  isolation: acme/leak: awaywork-leak has claude 2.1.290 (Claude Code stand-in), codex codex-cli 0.162.1 (stand-in)
```

The image is yours to build, and all the units get:

- **The agent CLIs and toolchain** the repo's rules use, and the commands of its stdio [MCP servers](../config/mcp.md), which start inside. Not `gh` or `glab`: awaywork's forge calls run outside. Install system-wide, not under `/root`. awaywork skips the `ENTRYPOINT`.
- **One per repo:** under `container`, a `repos` entry without `image` is an error, and a unit in a repo with no entry is skipped (`no image for acme/web: isolation: container needs one in its repos entry`). Nothing falls back to you.
- **Pulled once**, by the first `docker run` or `doctor`; `docker pull` to update.
- **Only the env it needs:** the image's, awaywork's placeholders, git config and prompt path, and that phase's secrets by name, never on argv. Nothing else of yours, ssh agent included.
- **A `HOME` in the clone,** `.away/home`, fresh per clone: what setup puts there reaches the chain, then goes. Bake caches into the image.
- **Logins:** Claude needs `CLAUDE_CODE_OAUTH_TOKEN`, Cursor `CURSOR_API_KEY` (its `HOME` is `.away/agent-home`). Codex gets your `auth.json` (`~/.codex`, `$CODEX_HOME` or `config_dir`) for the run, copied back after under its probes' lock when it's a refresh of the one lent, since a refresh rotates it ([Providers](../../providers.md#codex)). Probes and `--version` checks run on your machine.
- **Clones in your home,** in the run dir, not `/tmp`: the one place Colima and Docker Desktop both share. `doctor` fails if the engine can't mount it.
- **Removal:** each container is gone before awaywork reads the clone, `docker rm -f` on a timeout, the window's end or Ctrl-C. No answer from docker within a minute, and the clone is lost. `awaywork replay` runs in one too.
- **The network:** an internal Docker network and awaywork's proxy, [below](#the-network-in-a-container). The first run or `doctor` pulls the official Node image the wall needs.
- **Cost:** an image per repo to keep current, a few hundred ms per command on Colima, slow file sharing on macOS, and Linux only: no Xcode.

### The network in a container

Every container joins one internal Docker network: it has no route out, Docker's DNS answers nothing for outside names, and the bridge gets no address on the docker host (`inhibit_ipv4`, IPv6 off), so the host's own services, sshd and dev servers, are not reachable through the network's gateway [V, tested on Docker Desktop 28.3.2, Colima 0.8.1 and inside Colima's VM as native Linux, Docker 27.4.0]. Without that option the gateway answers with the host's services on all three. Its only other member is a forwarder, a container of the official `node:26-alpine` image, pinned by digest, running a few lines of awaywork's own that pipe each connection to awaywork's proxy on the host. The forwarder also sits on Docker's default network, so it is the only way out. Every launch gets the same `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` as under `user`, pointing at the forwarder, and the proxy applies the [same phase lists](#the-network-under-user): setup gets the registries and `network`, checks and the agent shell what the table there says.

- **The token:** the forwarder's side of the proxy listens beyond loopback, so awaywork gives each process a random token in the proxy URL (`http://awaywork:<token>@awaywork-egress:3128`) and the proxy answers nothing without it, on its loopback listener too, which on a Mac a container reaches through `host.docker.internal` [V, tested]. curl, git, npm, pip, wget and Node's `fetch` take the URL as is [V, tested]. What runs in the container reads it from its env, as it reads its login.
- **Where the proxy listens:** on Docker Desktop and Colima, and wherever the bridge's gateway isn't an address of this machine, the loopback, which the engine's `host-gateway` reaches [V, tested on Docker Desktop 28.3.2 and Colima 0.8.1]. Where docker runs on the machine awaywork does (Linux), the default bridge's gateway (`docker0`, `172.17.0.1` unless you changed it), never `0.0.0.0`; there the forwarder's `host.docker.internal` is that address, not Docker's own `host-gateway`, which Colima points at the Mac [V, tested inside Colima's VM, Docker 27.4.0].
- **Fails loudly:** before a run raises the wall it removes what a dead awaywork left, and then probes it with throwaway containers: one on the network must be refused at once connecting to `1.1.1.1:443` and to the proxy's own address on the host, resolve neither `registry.npmjs.org` nor `host.docker.internal`, and connect to no port of its network's gateway, one of them a listener on the docker host's own network (`docker run --network host`) that the probe starts, and reach the forwarder, which must ask for the token and, given it, refuse a host outside any phase; one on Docker's default network must reach `1.1.1.1:443` and that listener, or the probe can't tell. If any of it fails the run is refused before any model call, with the reason, and `doctor` fails the same way (its `network wall` line, above).
- **Cleanup:** the network and the forwarder go when the run does, also when awaywork dies on an exception. A kill leaves them, labelled `awaywork.wall=<host>:<pid>`, and the next start removes those of this machine whose process is gone.
- **The agent's shell:** Docker's default seccomp keeps Claude's and Codex's sandboxes from starting, so their shell gets the CLI's hosts and `network` through the wall rather than its own list, and Cursor's sandbox is left out, as [behind the wall under `user`](#cursor-s-shell-is-offline).
- **Proxy-ignoring clients:** they fail to resolve or connect even for an allowed host, with no line in `worker.log`, as under `user`. A refused host leaves `network: refused <host>:<port> (setup)`.

## What each key does

Four keys depend on the mode. Cells say what the key does to the agent's shell, setup, the checks (`verify`, `when`, `until` and gate scripts) and MCP servers. On a GitHub-hosted runner and in awaywork's image the mode is `user`, whatever `isolation` says.

| Key | `none` | `user` | `container` |
| --- | --- | --- | --- |
| [`network`](../config/repos.md) | Walls the shell to the hosts; setup, checks and MCP servers stay open | Walls everything the worker runs: setup, checks, the agent CLI and MCP servers reach only their phase's hosts ([below](#the-network-under-user)) | Walls everything a container runs: setup, checks, the agent CLI and MCP servers reach only their phase's hosts, through awaywork's proxy ([below](#the-network-in-a-container)) |
| [`writable`](../config/repos.md) | Opens the paths to the shell; the rest needs no grant | Same, and the worker user's file permissions still apply | No effect: host paths aren't there |
| [`serve`](../config/repos.md) | Starts the app for a step with `serve: true`, as you; the agent's MCP servers and its Codex and Cursor shells reach it, Claude's shell on Linux [doesn't](#claude-s-shell-is-offline), setup and checks don't | No effect: the step runs without the app | No effect: the step runs without the app |
| [`image`](../config/repos.md) | No effect | No effect | Setup, the shell, checks and stdio MCP servers run in it |

Under `none`, `network` and `writable` need the agent's own sandbox ([Claude](#claude-s-shell-is-offline), [Codex](#codex-s-shell-is-offline), [Cursor](#cursor-s-shell-is-offline)): where it can't start, the unit is skipped before any model call, with what to install in its reason, and `doctor` fails. Under `user` the [network wall](#the-network-under-user) stands in for it. Under `container` the [network wall](#the-network-in-a-container) does the same. In awaywork's image the wall is `user`'s, and the same refusal applies. A command provider has no sandbox and is never skipped for it: `network` and `writable` do nothing for its shell, and under `user` or `container` the wall limits it to the hosts of its phase. On an untrusted author's PR or issue the shell gets no hosts and no `writable` paths and `serve` isn't started; `image` still applies. For a key that does nothing in the mode, `doctor` prints `writable: no effect under isolation: container (top level, acme/api)`: an info line, once per key, naming where it's set.

## Not a sandbox

With `isolation: none`, the default on your machine and a self-hosted runner, all of the above keeps credentials out of the agent's way, not its reach. It runs as you, and its tools aren't sandboxed, except the agent's shell in Claude, Codex and Cursor ([below](#claude-s-shell-is-offline)): Claude Code has file tools pre-approved, Codex and Cursor run their shell open where their sandbox doesn't start (Cursor: no `--force`), a command provider whatever your command does. So what it reads can leave [I, from the code]:

- `~/.config/awaywork/.env`, with your `GH_TOKEN` and tracker tokens.
- gh's login, by unsetting the placeholders (an empty `GH_CONFIG_DIR` doesn't hide a keyring from `gh auth token`); `glab`'s keyring login needs nothing unset. Git credential helpers too: the worker's config names none, but your `~/.gitconfig` and the system one are readable, and a helper answers when run directly.
- twg's login in `~/.config/twg`: the empty `TWG_CONFIG_DIR` only points twg elsewhere. Its encrypted storage, keyed from your OS keychain, is untried with the empty dir; `doctor` warns.
- Your ssh keys and agent: no `SSH_AUTH_SOCK`, but the socket can be found (`launchctl getenv SSH_AUTH_SOCK` on macOS). On [Bitbucket](../config/sources.md#bitbucket-and-jira) those keys push, so a worker reading `~/.ssh` can push as you.
- A VS Code terminal's git askpass (`VSCODE_GIT_*`).
- On Linux, awaywork's own env under `/proc`, `GH_TOKEN` included: on a self-hosted runner, your personal access token.

Also open:

- **Prompt injection.** Untrusted authors' GitHub comments are [hidden](./index.md#public-repos), but issue bodies, CI logs, check names and links, other sources' text and trusted people's quotes may be anyone's. The harness calls them data; a model can still be talked into things, with the reach above.
- **Hooks and MCP servers across a loop's rounds:** on your repo, Claude Code loads the clone's `.claude/settings.json` and `.mcp.json`, and starts their servers unapproved, outside its sandbox and with its whole env [V, tested on macOS, Claude Code 2.1.327]. Claude's and Codex's sandboxed shells can't write them, nor can a walled Cursor write `.claude/settings.json`; but a walled Cursor can write `.mcp.json`, and setup and any agent whose sandbox doesn't start can write both, so a round can leave hooks or servers the next runs. A `.mcp.json` committed to your own repo starts its server the same way; awaywork doesn't change that.
- **MCP secrets in Claude's Bash where its sandbox doesn't start**, on your items ([MCP servers](./index.md#mcp-servers); [#155](https://github.com/AndreaProvenzale/awaywork/issues/155)). Cursor's shell can read them from its `mcp.json`.
- **The app `serve` starts** runs as you, with your env less every secret awaywork names, so it reaches what you reach. A process it detaches and leaves behind after exiting before it was ready can outlive the step. Only under `none`: not under `user`, `container`, a GitHub-hosted runner or awaywork's image, which don't support it yet.
- **Codex and Cursor read a PR author's `AGENTS.md`**, Cursor also `CLAUDE.md`, `.cursor/rules` and skills.
- **A command provider's repo config** on an untrusted author's PR, e.g. MCP servers or hooks in its config dir.

### Claude's shell is offline

Whatever the isolation, Claude's Bash runs in Claude Code's own sandbox: no network unless [`network`](../config/repos.md) lists hosts (top level, repo and rule add up; `*` opens all), and the login and the unit's MCP secrets unset in each command. `allowUnsandboxedCommands` is off, so the agent can't retry outside it, and with that off the clone's own settings can't widen the sandbox [V, tested on macOS, Claude Code 2.1.327]. It unsets the login in the environment only: a login file in `~/.claude` stays readable to its Bash. The agent CLI itself still reaches its API. Loopback is open where Claude runs on macOS, so tests can start a server and reach it, from a later command too; that opens every loopback port on the machine to it (your dev servers, databases) and the Mac's own LAN IP, on an untrusted author's PR too (hosts are withheld there, loopback isn't), while outside hosts stay closed. `sandbox.network.allowLocalBinding: false` in your [`settings`](../config/providers.md) closes it. On Linux each command has a loopback of its own: tests reach a server started in the same command, not yours nor one an earlier command left running [V, tested on both]. A host outside the list is refused and leaves `network: refused <host> (agent shell)` in `worker.log`, so you know what to add [V, tested on macOS and Linux, Claude Code 2.1.328]. Hosts go through the sandbox's proxy, and names don't resolve inside it: a client that ignores `HTTPS_PROXY` (`curl --noproxy`, Node's built-in `fetch`) stays offline even under `*`, with no line in `worker.log` [V, tested on both]. The filter is by hostname: an allowed host is a way out, and the judge gate's Claude never gets the list. Commits and tests work through it [V, tested on macOS and a hosted runner]. Its Bash writes only the clone, its own temp dir and, under `user`, the worker's `/tmp/awaywork-*` `HOME`, which awaywork allows with `sandbox.filesystem.allowWrite`; `/tmp` is read-only [V, tested on a hosted runner]. Under `none` it can't write `HOME` either, so tools that cache there (Go's build cache, `npx`, pnpm's store) fail unless [`writable`](../config/repos.md) lists the folder; under `container`, `HOME` is in the clone.

It needs Seatbelt on macOS, and bubblewrap, socat and unprivileged user namespaces on Linux; without socat Claude turns its sandbox off itself and Bash runs open [V, tested on a hosted runner]. Before a Claude unit runs where Linux does (as the worker user, as you, or in the container, on a macOS host too), awaywork runs the namespaces and mounts Claude's sandbox sets up there, once per process for each image or user: `bwrap --unshare-user --unshare-net --unshare-pid --ro-bind / / --proc /proc --dev /dev bwrap --unshare-user --ro-bind / / socat -V`. The inner `bwrap` stands for the user namespace Claude's `apply-seccomp` helper nests, which AppArmor can refuse where the outer one starts; `socat -V` fails where socat is missing. If it fails, the sandbox is left out, the unit's `worker.log` says so, and Bash runs unsandboxed, shell open, rather than every command failing. `doctor` runs the same probe, in each repo's image under `container`. That's the case:

- **On a default Docker,** including awaywork's image, which has no bubblewrap. [V, tested by hand in containers on Colima, Claude Code 2.1.327: the probe and Claude's Bash agreed on a default container, one with seccomp and AppArmor unconfined, and root with `SYS_ADMIN`, where both fail on the masked `/proc`.] A container can also refuse the nested namespace after the outer one starts [V, once, with `systempaths=unconfined`].
- **On a GitHub-hosted runner without the action,** `ubuntu-latest` has bubblewrap and no socat, and AppArmor's `bwrap-userns-restrict` profile lets bwrap start but refuses the nested namespace, so every Bash call would fail with `apply-seccomp: write /proc/self/setgroups`; the probe fails there and the shell stays open [V, tested: the probe and awaywork's Claude provider on a runner]. `ubuntu-24.04` has no bubblewrap, and once installed its outer bwrap fails (`loopback: Failed RTM_NEWADDR`); `ubuntu-22.04` passes with bubblewrap and socat installed [V, tested]. Setting `kernel.apparmor_restrict_unprivileged_userns=0` alone doesn't help; unloading the profile does [V, tested]. The action does the work when Claude is installed: it installs bubblewrap and socat and, where that sysctl is 1, puts a copy of bwrap at `/opt/awaywork/bin/bwrap` first on `PATH` with a profile of its own that grants `userns`, so Claude and awaywork's probe both find it, and the system bwrap stays as Ubuntu ships it. Then the probe passes as the worker and Claude's Bash runs sandboxed: offline, secrets unset, `/tmp` read-only, commits work [V, tested on `ubuntu-latest` (26.04), 24.04 and 22.04, Claude Code 2.1.330: the probe passed as the worker, and a real run saw the label `awaywork_bwrap`, no network, no secrets, `/tmp` read-only]. The cost: any local user, the worker included, can run that copy and get a user namespace with capabilities in it, which Ubuntu's restriction exists to stop [I]; Cursor's step does the same for its helper.

Where the sandbox does run, it leaves an empty `.git/objects/info/alternates` and `.git/config.worktree` and `.claude-sandbox-noreplace` folders under `.git` [V, tested on a hosted runner]. awaywork removes the empty `alternates` when it puts the clone's git config back, and still refuses one with content or a link. Setup, checks and MCP servers stay open.

So run awaywork where that's acceptable, or give it a [worker user](#a-worker-user-on-your-linux-machine) on Linux or a [container](#a-container-on-your-machine) wherever Docker runs. GitHub's hosted runners [always get a worker user](#a-worker-user-on-github-hosted-runners) and the action starts Claude's sandbox there; [awaywork's image](#a-worker-user-in-awaywork-s-image) also gets a worker user but doesn't start it.

### Codex's shell is offline

Codex runs with a permissions profile instead of `--sandbox danger-full-access`: its shell reads everything, writes the clone (`.git` too, so commits work), the temp dir and, under `user`, the worker's `HOME`, and reaches only the [`network`](../config/repos.md) hosts through Codex's proxy, none by default; `*` opens all, `*.x` is x's subdomains. Loopback stays open for test suites. A refused host fails the command with `Network access to "<host>" was blocked: domain is not on the allowlist for the current sandbox mode.`, which the model reads, and leaves `network: refused <host> (agent shell)` in `worker.log` (the first host of a command only; when Codex rejects a command before it starts, the line comes from its stderr). Names don't resolve inside it: a client that ignores `HTTPS_PROXY` stays offline even under `*`. The agent CLI itself still reaches its API, and a unit on an untrusted author's PR gets no hosts. MCP servers run outside it, and their tools are approved without asking, since a profile fails any tool that isn't read-only otherwise. A clone's `.codex/config.toml` can't widen the hosts: `--ignore-user-config` keeps it unread [V, tested on macOS, Codex 0.162.1, a file allowing pypi.org and httpbin.org]. The filter is by hostname: an allowed host is a way out. The clone's `.claude`, `.mcp.json`, `.codex` and `.agents` are read-only to it, so it can't plant hooks or MCP servers for a later round, nor edit a repo's own Codex skills. Under `none` it can't write `HOME` either, so tools that cache there (`npm install` needs `~/.npm`) fail even with their host listed, unless [`writable`](../config/repos.md) lists the folder; under `container`, `HOME` is in the clone.

On Linux it needs bubblewrap and unprivileged user namespaces. Before a Codex unit runs there, awaywork runs `bwrap --unshare-user --unshare-net --unshare-pid --ro-bind / / --dev /dev true`, once per process for each image or user; if it fails, the unit's `worker.log` says so and the shell runs open, as for Claude, since Codex fails every command otherwise (`bwrap: No permissions to create new namespace`). `doctor` runs the same probe. Codex looks `bwrap` up on `PATH` before its bundled copy, so on a hosted runner where the action put its bwrap copy first for Claude, Codex's shell and the probe use that copy too, so on `ubuntu-latest` and 24.04 its commands run under the copy's unconfined `awaywork_bwrap` profile, as Claude's do, behind the wall [I, not exercised for Codex behind the wall]: `ubuntu-latest` starts with either bwrap, 24.04 only with the copy, and 22.04, where the sysctl is 0, gets no copy [V, tested on Codex 0.171.0 with `codex sandbox` under strace: `/opt/awaywork/bin/bwrap` ran with the copy first, `/usr/bin/bwrap` without]. In a default Docker container the probe fails and the fallback commits, reaches any host and writes `HOME`; with the VM's `kernel.apparmor_restrict_unprivileged_userns=0` and `seccomp=unconfined`, `apparmor=unconfined` it passes and the shell is walled [V, tested on Colima, Codex 0.162.1]. Under `user`, awaywork sets `TMPDIR=/var/tmp` for Codex, handed to the worker through sudo's argv since sudo drops it: with its `CODEX_HOME` under the temp dir it won't make its sandbox helper, and every command fails. Where the clone has no `.claude` or `.mcp.json`, Codex shows them as empty files inside, so awaywork points git's `core.excludesFile` at a file outside the clone for Codex's shell, and a commit leaves them out; the clone's own `.git` is never written (under `none` that replaces your global git ignore for the shell) [V, tested on Colima under `user`, Codex 0.162.1].

### Cursor's shell is offline

Whatever the isolation, Cursor's shell runs in Cursor's own sandbox: no network unless [`network`](../config/repos.md) lists hosts (top level, repo and rule add up; `*` opens all), and writes only the clone, its temp dir and the [`writable`](../config/repos.md) paths (`additionalReadwritePaths` in the same `sandbox.json`; its `HOME` is in the clone, so what it caches there starts cold). awaywork turns it on in the run's `cli-config.json` (`sandbox.mode: enabled`, `networkAccess: user_config_only`, which drops Cursor's built-in list of registries and GitHub), writes the hosts to a `.cursor/sandbox.json` in the run's `HOME`, and leaves `Shell(*)` out of `allow`: a command that matches an allow rule runs unsandboxed. The agent CLI itself still reaches Cursor's API. A host outside the list is refused and leaves `network: refused <host> (agent shell)` in `worker.log`, read from Cursor's decision log once the step ends; a subagent's shell is walled too, but its refusals don't reach the log. Names don't resolve inside it: a client that ignores the proxy (`curl --noproxy`, Node's built-in `fetch`) stays offline even for an allowed host. Loopback is always on the list, as macOS's sandbox refuses it otherwise: test suites can bind and connect there. Commits run through it. [V, tested on macOS and Linux, Cursor 2026.11.19]

`*.x` opens `x` too, where Claude's means the subdomains only: list `x` alone if that's all you want.

A clone's own committed `.cursor/sandbox.json` would add its hosts, and Cursor re-reads it for each command. So awaywork sets it aside for the run: moved out, kept out of the unit's commits, put back before anything is published, and `worker.log` and `awaywork report` say `network: set aside .cursor/sandbox.json (adds pypi.org)`. The edit tool is denied `**/.cursor/**` for the same reason, and `**/.claude/**`: it runs outside the sandbox, and Cursor loads Claude Code's `.claude/settings.json` hooks at the next step's start, unsandboxed [V, tested on macOS: a hook the edit tool wrote ran with the network open in the next step]. The sandboxed shell can't write `.cursor/sandbox.json`, `.cursor/hooks.json` or `.claude/settings.json` and `settings.local.json`, but writes other files in `.claude/` [V, tested on macOS]; Cursor's own profile exempts `.cursor/(rules|commands|worktrees|skills|agents)` from its `.cursor` write deny [V, profile text, not run]. The cost: the edit tool can't edit `.cursor/rules`, `.cursor/skills` or the repo's Claude config (`.claude/`). On someone else's PR the clone's file is hidden like the author's other Cursor config, and the unit gets no hosts, unless its author is trusted. The prompt tells the model it is sandboxed: asked to leave it, Cursor refuses, which cost a turn in 4 of 28 calls.

It needs Seatbelt on macOS and unprivileged user namespaces on Linux. Before a Cursor unit runs, awaywork runs the helper beside `agent` the way Cursor's own startup check does (`cursorsandbox --policy … --preflight-only -- /bin/true`, no model call), once per process for each image or user, as the worker user, as you or in the image. If it fails, the sandbox is left out, the unit's `worker.log` says so, and the shell runs open with `Shell(*)` rather than the run failing at startup; `doctor` runs the same probe. That's the case on a default Docker, including awaywork's image [V, tested in Colima: probe exit 2, then the open shell ran]. It starts with `kernel.apparmor_restrict_unprivileged_userns=0` and, in Docker, `seccomp=unconfined` and `apparmor=unconfined` [V, tested in Colima]. On GitHub's `ubuntu-latest` the action loads an AppArmor profile for the helper (`userns,` only), so it starts without opening user namespaces to every process.

### The network under `user`

Under `user` the kernel leaves the worker user loopback and nothing else, and awaywork runs a small proxy there that connects only to the hosts of the phase that runs. Every launch gets `HTTPS_PROXY` and `HTTP_PROXY` (and their lowercase forms) pointing at it and `NO_PROXY=localhost,127.0.0.1,::1`, `NODE_USE_ENV_PROXY=1`, so Node's `fetch` takes the proxy too (Node 22 prints an `[UNDICI-EHPA] Warning: EnvHttpProxyAgent is experimental` line to stderr for it; a test asserting empty stderr sees it behind the wall), replacing any proxy variables of your own: the proxy connects straight out and doesn't chain to a corporate one, and `doctor` warns when yours are set. A client that ignores the proxy is refused. Names don't resolve for the worker: DNS is refused on port 53, and the lines below deny it systemd-resolved's varlink socket and its D-Bus name, which `iptables` can't see. Hosts match as in [`network`](../config/repos.md): a name exactly, `*.x` its subdomains, `*` everything.

| Phase | Hosts |
| --- | --- |
| Setup | the package registries (`registry.npmjs.org`, `registry.yarnpkg.com`, `pypi.org`, `files.pythonhosted.org`, `proxy.golang.org`, `sum.golang.org`, `crates.io`, `static.crates.io`, `index.crates.io`, `rubygems.org`) and GitHub for git dependencies (`github.com`, `codeload.github.com`, `objects.githubusercontent.com`, `release-assets.githubusercontent.com`), plus `network` |
| The agent CLI | its vendor's (Claude: `api.anthropic.com`, `platform.claude.com`, `claude.ai`; Codex: `chatgpt.com`, `auth.openai.com`, `api.openai.com`; Cursor: `*.cursor.sh`, `*.cursorapi.com`, `*.cursor-cdn.com`), the host of each HTTP MCP server's `url`, `network`, and each stdio server's [`network`](../config/mcp.md) |
| `verify`, `until`, `when`, gate scripts | `network` |
| A gate's judge | its vendor's |

The built-in setup list is on and not configurable. An allowed host takes any port, and a destination that is link-local after resolution (`169.254.0.0/16`, where clouds keep their metadata service, and `fe80::/10`) is refused, under `*` too. Every other address is reached under `*`, your machine's loopback services and the LAN included, since the proxy runs as you. On an untrusted author's PR setup doesn't run; on their issue it does, with the registries alone. Their checks and agent get no `network`, and the agent gets its vendor's hosts alone. A refused connection fails the client's request (a 403 for the proxy's clients, or a closed connection where the destination turned out link-local) and leaves `network: refused <host>:<port> (<phase>)` in the unit's `worker.log`, once per host and phase. A `verify` has no log of its own: its refusal shows in `verify.log` as the command's own failure. A CLI's optional calls are refused too and logged: Codex's `ab.chatgpt.com` and `*.oaiusercontent.com` [V, tested, Codex 0.171.0], which it runs without. Claude's telemetry would be, and awaywork turns it off behind the wall (`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`).

The rules are the part you run. For a worker user `awaywork` they are the lines below, for IPv4 and IPv6: loopback is open, so the proxy and a test suite's own servers stay reachable, except port 53, where a resolver such as systemd-resolved would answer for the worker; everything else the worker sends is rejected. Two more lines deny the worker systemd-resolved's varlink socket (a file ACL on `/run/systemd/resolve`) and its D-Bus name (a policy file); the ACL needs the `acl` package, which the lines install on Debian and Ubuntu (elsewhere install it first). `doctor` prints them for your worker user until the probe passes; `run` refuses the same way, before any phase, and the daemon probes again at each run. The probe first has awaywork itself connect to `api.github.com` and resolve it, so it can tell; then, as the worker, the connection must be refused at once (not time out) and the name must not resolve by `getent`, nor through systemd-resolved's socket or D-Bus name (`busctl call … ResolveHostname`; the ACL and policy are what's probed), and no nscd socket may be writable to it. IPv6 gets the same where awaywork's own user has a route. A box where awaywork can't reach `api.github.com` proves nothing, and counts as no wall.

### A worker user on your Linux machine

With [`isolation: user`](./isolation.md), setup, the agent and the checks run as `awaywork`, a user you make once (`awaywork-work` under a profile `work`, and so on for each: a profile name of 23 characters or fewer, as Linux limits user names to 32). As on a [hosted runner](#a-worker-user-on-github-hosted-runners), the clone is the worker's only while repo code runs, awaywork kills all the worker's processes after each phase, and its own git runs only on a clone that's yours again. Without the user or the sudoers lines, `run` refuses rather than run as you. It closes:

- **Your files:** the env file, gh's `hosts.yml`, `~/.ssh`, `~/.gitconfig` and the rest of a home closed to others (`chmod o-rwx ~`; `doctor` warns until then).
- **Logins in other processes:** `/proc/<pid>/environ` is owner-only, your ssh agent's socket sits in a folder only you can enter, and gh's keyring answers over your session bus in `/run/user/<uid>`, closed to other users [C, not exercised: the test container has no keyring].
- **A way back in:** no sudo, cron or `at`, a `nologin` shell, so no `ssh` or `su`: once its phase is killed, nothing of it runs.
- **What one unit leaves the next:** its `HOME` is a fresh `/tmp/awaywork-XXXXXX` per clone, removed with it; there's no `/home/awaywork`. An `~/.npmrc`, a Claude hook or a shim in `~/.local/bin` never reaches another repo.
- **A swapped clone:** `/tmp` is sticky, so the worker could rename its folder and leave a link to yours. After each phase awaywork checks clone and home are the same folders (`lstat`, same inode) and closes them (`chmod -R u+rwX,go-rwx`, top folder `711` for the next phase; a fresh clone is `700`). Otherwise the clone is lost: no more phases, no git of awaywork's, nothing published.

A lost clone keeps the worker's `.git`, config and hooks: run nothing in it, as with [replay's](../skills.md#try-an-edit-on-a-past-unit); `git fetch <clone> <branch>` from your checkout runs nothing of it. Tried: a worker that moved its clone or `HOME` and linked one of the developer's repos there lost the clone, and that repo's `.git/config` was untouched; `chmod 777` on the clone, its `.git` and `~` left `711`, `700` and `711`, unwritable to another local user.

A real run in a Debian 12 container, a leak script as the agent, the developer's home at 755. With `none` it read the env file, the home, gh's `hosts.yml` and the ssh agent, and left a detached `sleep` running after the run. With `user`, after `chmod o-rwx ~`:

```
agent: as awaywork (awaywork), HOME=/tmp/awaywork-6etN3Q, cwd=/tmp/awaywork-lLAmqr
agent: ok   the env file
agent: ok   the developer's home refused
agent: ok   awaywork's env /proc/10571/environ
agent: ok   any /proc/*/environ
agent: ok   gh's hosts.yml
agent: ok   the ssh agent at /tmp/ssh-*/agent.*
agent: ok   sudo -n true refused
agent: left a detached sleep 4242 behind
```

Nothing of the worker's was left running, nor any folder. (At 755, the home and `hosts.yml` still leaked.)

The sudoers lines give your user no more than that. The first runs anything as the worker, which can do nothing you can't. The second is all awaywork runs as root, `chown -R` of a clone to the worker and back; a loose rule there would let anything running as you chown `/etc/shadow` to the worker. So:

- **No `*`:** sudoers' `*` matches spaces, so `/tmp/awaywork-*` also allowed `/tmp/awaywork-x /etc/hostname`, which chowned it. Six character classes match six letters or digits, on any sudo.
- **Straight under `/tmp`:** a deeper rule loses to a link; with `/tmp/awaywork-??????/work/*` allowed, a `work -> /etc` link chowned `/etc/passwd`.
- **No link followed:** `-h -P` changes links themselves, and `doctor` and `run` refuse a kernel with `fs.protected_hardlinks` off.
- **No env:** the root line has no `SETENV`, so sudo refuses `--preserve-env=PATH` and drops `LD_PRELOAD`.

Tried with only those two lines (sudo 1.9.13p3):

- Everything but the exact two commands asked for a password: `/etc/shadow`, a seventh character, `../`, a space, a second path, `-L`, `root:`, `-u root`, `-g root`.
- The same words split differently passed sudo, and `chown` refused them.
- Through links to `/etc` and `/etc/shadow`, only the links changed; `ln /etc/shadow` failed.
- 30 rounds of a loop swapping folders for links to `/etc` changed nothing there.
- No file under `/etc` ended up anyone's but root's.

Still open:

- **The network,** to the [allowed hosts](#the-network-under-user), each of them a way out, and loopback.
- **The worker's own login,** in its env as it must be: `CLAUDE_CODE_OAUTH_TOKEN`, `CURSOR_API_KEY`, or a copy of your Codex `auth.json` in its `HOME` ([the lent Codex login](#the-lent-codex-login)).
- **`/tmp`:** every unit of a profile is the same user, so a file left in `/tmp` or `/var/tmp` outside its folders is there for a later unit. Nothing runs it unless something looks.
- **The machine:** localhost services answer it, and anything world-writable is a place to plant a binary you run later. Hosted runners clear that bit; on your machine `find / -xdev -perm -o+w ! -type l ! -perm -1000` lists them.
- **Other developers:** the `chown` line reaches any awaywork clone, so one developer per worker user. Each profile of one developer has a worker user of its own, so ending a phase kills only that profile's processes. A unit holds its worker user's lock (`workers/<user>.lock` in the root state dir) from its first phase to its last, so units of one worker user take turns, and profiles sharing `awaywork` do too.

#### The lent Codex login

awaywork has no Codex login of its own and lends the file your `codex` uses (`$CODEX_HOME/auth.json`, env file included, else `~/.codex/auth.json`). Since a refresh rotates it, awaywork saves back only a refresh (tokens and `last_refresh`), refused when the mode, API key or account differs, and only while yours is still the one lent.

The tokens are the worker's word, though: a hostile worker can return another account's, labelled with your `account_id`, and your Codex then runs on that account, awaywork's runs and your own sessions, prompts and code included, until you `codex login` again. Codex being experimental, that ships as is; [#315](https://github.com/AndreaProvenzale/awaywork/issues/315) tracks a login it can't swap.

### A container on your machine

With [`isolation: container`](#in-a-container), every setup, agent run and check runs in a fresh container of the repo's image that sees the clone and the skills plugin and nothing else. That's not a list of things to hide, so it closes more, on a Mac too:

- **Your files:** only the clone in your home is mounted: no env file, `hosts.yml`, `~/.ssh`, `~/.gitconfig` or keychain files, and no `security` to ask the keychain.
- **Other processes:** its own `/proc`, never awaywork's env. Neither the ssh agent's socket nor the docker socket is mounted, so no container of its own with your disk.
- **Root inside:** your uid and gid, no capabilities, `no-new-privileges`, so a setuid `sudo` goes nowhere, even with `NOPASSWD: ALL`. Setuid files it makes are yours and Colima keeps the bit, so awaywork drops it when copying `.away` out, and the run dir is `700`.
- **Your env:** the image's, awaywork's placeholders and git config, and that phase's secrets by name (`-e NAME`, never on argv), nothing else of yours.
- **Nothing outlives its phase:** a container goes with its command, and awaywork `docker rm -f`s it on a timeout, the window's end, Ctrl-C or the watchdog. If one may still be running, listed or docker silent for a minute, the clone is lost, as with the worker user: nothing is published from it, awaywork leaves it alone and saves no Codex login back from it. A lost clone may still have a container: run nothing in it.

- **The network:** what it reads, it can send to the hosts of its phase, and an allowed host is a way out (the registries, GitHub and the vendor's API with an account of the attacker's own, by hostname only, so domain fronting works). The LAN, Docker Desktop's `host.docker.internal` and your Mac's services are not reachable except through the proxy, which asks for its token on every listener [V, tested]; the token is in the container's env, so what runs there can use the proxy as the agent does. The proxy runs on your machine, so `*` reaches everything but link-local through it: your loopback services and the LAN too, and so does a listed name that resolves to a private address. Other containers on the default network reach the proxy's listeners, and need the token. Rootless docker and a remote `DOCKER_HOST` aren't supported: the probe fails with that in its reason [I, not run]. The forwarder's image comes from Docker Hub, pinned by digest.
- **The agent's secrets:** its token, Codex's `auth.json` for the run, its MCP servers' secrets. The Codex login it hands back has [the worker user's](#the-lent-codex-login) limits.
- **The clone:** what a phase leaves is what checks run and awaywork publishes, though awaywork restores git config and refuses links after each phase.
- **The image:** a token baked into a layer or `.npmrc` reaches every unit.
- **The kernel:** a container shares the VM's kernel, on Linux your machine's: it's a namespace, not a VM, and a kernel bug is a way out. On a Mac that lands in the VM, and Colima mounts your whole home read-write (`colima ssh -- mount` shows `/Users/<you>` over sshfs, `rw`), so the VM is no second wall.
- **Memory on a Mac:** the watchdog watches your Mac, not the VM, whose OOM killer can take `dockerd` and lose the clone. The disk floor holds.

### A worker user on GitHub-hosted runners

A hosted runner is where your classic token meets issue text unattended, with passwordless sudo, so repo code never runs as you there. Setup, the agent and the checks run as `awaywork`, made by the action, always:

- **A user with nothing:** no sudo, `docker`, other groups or crontab.
- **A locked runner:** the runner's home is `chmod 700`, with your checkout, step scripts, `RUNNER_TEMP` and `GITHUB_ENV` (the env of later steps).
- **Nothing world-writable:** the action clears the bit on some 800,000 paths (`/usr/local/bin` and the toolcache's `node` among them, where the worker could plant a `gh` awaywork runs with your token) and on the default ACLs of some 36,000 folders. Under two minutes, mostly disk reads.
- **A safe kernel:** it refuses one with `fs.protected_hardlinks` or `fs.protected_symlinks` off (both on in GitHub's image).
- **Only the clone is shared:** clones, per-clone `HOME`s and the plugin live in `/tmp`. A clone is the worker's while repo code runs, then the runner's again, checked to be the same folder and closed, before awaywork's git touches it.
- **awaywork's git** uses the clone's own `.git` only, never a repo above it in `/tmp`, and only once its config is awaywork's again. A `.git` turned into a link, with a symlink outside its hooks, or borrowing another repo's objects gets no more git and publishes nothing. A clone the runner can't take back (a failing `chown`) ends its chain unpublished and untouched.
- **Nothing outlives its phase:** awaywork kills all the worker's processes after each one.
- **No value on argv:** env goes through sudo by name (`sudo --preserve-env=PATH,CLAUDE_CODE_OAUTH_TOKEN,…`), and pushes use gh's credential helper, never a token in a URL.
- **Only loopback and a proxy:** `iptables` rules for the worker's uid, IPv4 and IPv6, from the same script: the worker reaches awaywork's proxy and nothing outside, [the network under `user`](#the-network-under-user).
- **No silent fallback:** without the user, say `awaywork run` without the action, it refuses: `can't run as the awaywork user on this GitHub-hosted runner: run awaywork through its action, which creates it`.

A spike tried every leak above from setup, a `when` check and two agent runs, with `GITHUB_TOKEN` as `GH_TOKEN`. As `runner`, all of them worked: awaywork's `/proc` env, `RUNNER_TEMP`, `GITHUB_ENV`, sudo, docker, crontab, planting in the toolcache, a leftover process. As the worker user:

```
agent: ok   any /proc/*/cmdline
agent: ok   gh auth token, GH_TOKEN and GH_CONFIG_DIR unset

agent: ok   GITHUB_ENV not writable
agent: ok   sudo -n true refused
agent: ok   docker refused
agent: ok   crontab refused
agent: ok   no PATH or toolchain dir writable
agent: ok   nothing left from an earlier phase
```

That spike predates per-clone `HOME`s, now a `/tmp/awaywork-XXXXXX`. Still open: the agent's own secrets (its token, its MCP servers'), the [allowed hosts](#the-network-under-user), the clone, what's world-readable (toolchains, `/tmp`, every command line but not env), and the disk and memory, where the watchdog stops the unit.

### A worker user in awaywork's image

The [container](../scheduling/container.md) for `awaywork watch` is built from awaywork's Dockerfile, which sets `AWAYWORK_IMAGE=1`: setup, the agent and the checks always run as `awaywork`, whatever `isolation` says. awaywork runs as `away`, whose env holds `GH_TOKEN`, so an agent running as `away` could read it from `/proc/1/environ`. Another image without the user refuses: `can't run as the awaywork user in this image: build it from awaywork's Dockerfile, which creates it`.

At build, the Dockerfile makes the worker as the action does: no sudo, cron or `at`, `nologin`, no home, `/home/away` `700`, world-writable bits and default ACLs cleared. `away` gets the two [`isolation: user`](#a-worker-user-on-your-linux-machine) sudoers lines, kept equal by a test. The kernel settings are the host's, checked at the daemon's first run. A stand-in agent:

```
agent: as awaywork (awaywork), HOME=/tmp/awaywork-W8BnHa
agent: ok   /proc/1/environ refused (/usr/bin/tini -- /usr/local/bin/awaywork)
agent: ok   /home/away refused
agent: ok   sudo -n true refused
agent: GH_TOKEN=none
agent: committed smoke.txt
```

The image holds the [network wall](#the-network-under-user) too. Its entrypoint runs `/usr/local/sbin/awaywork-wall` as root, the one script `away`'s sudoers lets it run: the hosted runner's eight rules plus one for Docker's resolver (below), for IPv4 and IPv6, in the container's own network namespace, where they last until the container is gone. It needs `NET_ADMIN`, which `compose.yml` asks for (`cap_add: [NET_ADMIN]`). Without it the script fails with a line in the container's output, the daemon stays up for `doctor` and `docker exec`, and a run is refused before any phase:

```
the network wall isn't up for the awaywork user (awaywork reaches api.github.com), so its setup, checks and MCP servers could reach any host: the rules are missing: the container needs NET_ADMIN for the wall, `cap_add: [NET_ADMIN]` in compose.yml
```

On a compose network `/etc/resolv.conf` names Docker's resolver, `127.0.0.11`, which Docker redirects to a port of its own before the filter sees the packet, so the rule for loopback's port 53 misses it and the worker resolved names [V, tested in Docker Desktop's VM, Docker 28.3.2: `getent -s dns hosts api.github.com` exit 0 for `awaywork`, and the probe said `awaywork resolves names`]. The script also rejects the worker's traffic to `127.0.0.11`, which closes it, and `away` and root still resolve [V, tested]. The image has no systemd-resolved, D-Bus or nscd, so the resolver lines aren't needed. A test keeps the script equal to the rules `doctor` prints elsewhere. On a shared box:

- **One container per developer:** everything is in one `GH_TOKEN`'s name, and the `chown` line is for one developer. A company box runs a container, control repo and token per person.
- **Host root reads every token:** `docker inspect` shows env, so a Coolify admin or anyone with `docker` has them all. Put your token only where you'd trust root.
- **Never mount the Docker socket:** whatever reaches it is root on the host, and every container's tokens with it.
